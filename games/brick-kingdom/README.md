# Brick Kingdom

NES 시대 사이드스크롤 액션 플랫포머. 엔트리 블록으로 구현한 **타일맵 · 서브스텝 충돌 ·
카메라 스크롤 · 상태 머신**을 갖춘 원작 감각의 점프 액션.

캐릭터·적·아이템·타일은 전부 이 저장소에서 만든 원본 픽셀아트다(아래
[에셋과 라이선스](#에셋과-라이선스) 참고).

| 항목 | 값 |
| --- | --- |
| 최신 `.ent` | [`brick-kingdom_002.ent`](brick-kingdom_002.ent) (31,246 bytes, 6 오브젝트) |
| spec | [`spec.mjs`](spec.mjs) (1,699 줄) |
| 레벨 데이터 | [`levels.mjs`](levels.mjs) — 356 열 × 12 행 (TILE=24) |
| 물리 상수 | [`physics.mjs`](physics.mjs) |
| 픽셀아트 | [`assets/sprites.mjs`](assets/sprites.mjs), [`assets/pixel-art.mjs`](assets/pixel-art.mjs) |
| 런타임 검증 | [`verify.mjs`](verify.mjs) — 16 시나리오 |

```bash
npm start
```

http://localhost:3000 에서 `games/brick-kingdom/brick-kingdom_002.ent` 를 열고 ▶ 실행.

## 조작

| 키 | 동작 |
| --- | --- |
| ← → | 걷기 (누른 시간에 따라 가속, 반대 방향은 스키드 후 반전) |
| ↑ 또는 Z | 점프 — **누른 시간에 비례해 높이가 달라진다** |
| X | 달리기 (최고 속도 2.34 → 3.75 px/frame = 걷기의 1.6 배) + 빔 상태에서 발사 |
| ↓ | 웅크리기 (히트박스 축소) |
| Enter | 타이틀에서 시작 / 게임오버 후 재시작 |
| P | 일시정지·재개 |

가속·마찰·스키드·공중 제어 감쇄를 모두 따로 두었고, **코요테 타임이나 점프 보정 같은
현대적 보조는 넣지 않았다** (요구사항 B).

## 구현 범위 (Phase 1 수직 슬라이스)

### 화면·상태

- 8 상태 머신: TITLE → READY → PLAYING → (PAUSED / DYING / STAGE_CLEAR) → GAME_OVER → ENDING → TITLE.
  끊김 없이 순환한다.
- HUD: 점수 · 코인 · 구역 · 남은 시간 · 생명.
- 사이드스크롤 카메라 — 플레이어가 화면 42% 지점을 넘으면 월드가 스크롤하고,
  **정상 진행 중 역스크롤하지 않는다**. 월드 좌표(`px`)와 카메라 좌표(`cam_x`)는 분리.

### 물리·충돌

- 고정 틱 물리. 위치·속도·중력·가속도·마찰·최대속도를 전부 별도 변수로 관리.
- **서브스텝 스윕 충돌** (`SUBSTEP=4`) — 최대 낙하 속도 12 px/frame 에서도 바닥을
  관통하지 않는다(검증됨).
- 타일 AABB 를 바닥 / 천장 / 좌벽 / 우벽으로 구분. 경사면 없음.
- 블록 아래에서 머리박기와 위에 착지를 다른 판정으로 처리.
- 사망 원인 4 종 구분: 추락(1) · 적 접촉(2) · 위험물(3) · 시간 초과(4).

### 플레이어 등급

| 등급 | 상태 | 피격 시 |
| --- | --- | --- |
| BASE (0) | 기본 | 사망 |
| BIG (1) | 성장 — 히트박스 높아짐, 벽돌 파괴 가능 | BASE 로 하락 + 무적 90 프레임 |
| BEAM (2) | 원거리 공격 가능 | 한 단계 하락 |

스타 아이템은 600 프레임 무적 — 접촉만으로 적을 처치한다.

### 블록·아이템

| 타일 | 이름 | 동작 |
| --- | --- | --- |
| `#` | 지형 블록 | 파괴 불가 |
| `B` | 벽돌 | **BIG 이상에서만** 머리박기로 파괴 |
| `?` | 보상 블록 | 머리박으면 내용물 배출 → `u`(사용됨)로 전환, 재사용 불가 |
| `u` | 사용된 블록 | 반응 없음 |
| `c` | 코인 | 겹치면 획득 |
| `P`/`p` | 파이프 | 지형 |
| `F` | 깃대 | 도달 시 STAGE_CLEAR |

아이템은 블록에서 **솟아오른 뒤**(24 프레임) 이동을 시작한다. 종류: 성장 · 빔 ·
스타(착지할 때 튄다) · 추가 생명.

### 적 (원본 디자인)

| 문자 | 이름 | 특성 |
| --- | --- | --- |
| `r` | 롤스톤 (8 마리) | 벽에서 반전. 밟으면 **셸**이 되고, 셸을 차면 날아간다 |
| `g` | 코그워커 (3 마리) | 절벽에서 돌아선다 (떨어지지 않는다) |
| `s` | 스파이크샤드 (1 마리) | **밟을 수 없다** — 밟으면 피격 |

- 판정 5 종을 따로 처리: 밟기 · 측면 접촉 · 블록 머리박기 · 발사체 · 무적 접촉.
- 이동 중인 셸이 다른 적을 치면 **연쇄 처치** (점수 200 × 연쇄 수).
- 연속 밟기 콤보 점수 상승 (100 × 콤보).
- **활성 범위** — 화면 좌우 64px 여유 안의 적만 물리·판정을 돈다.

### 스테이지 1-1 "구리 평원"

356 열 (11,392 px) · 제한 시간 400 초 · 목표 350 열 · 체크포인트 178 열.
지형 블록 831 · 벽돌 22 · 보상 블록 5 · 코인 12 · 파이프 2 조 · 적 12 마리.
원작 타일 배치를 복사하지 않고 새로 설계했다.

## 아키텍처

### 오브젝트 6 개 (요구사항 H: 역할 분리)

| 오브젝트 | 책임 |
| --- | --- |
| `sky` | 배경 |

### 복제본을 쓰지 않는다

적·아이템·발사체는 **고정 길이 병렬 리스트**(`en_*`, `it_*`, `sh_*`)에 담고
`actors` 오브젝트 하나가 전부 stamp 한다. 이 구조 덕분에 요구사항 F·H 의 두 가지
위험이 **구조적으로 불가능**해진다.

- "복제본별 상태가 섞이면 안 된다" → 복제본이 없다.
- "재시작 반복 후 오브젝트/복제본이 늘면 안 된다" → 리셋이 `setListAt` 으로
  **덮어쓰기만** 하고 `add_value_to_list` 를 쓰지 않아서 리스트 길이가 자랄 수 없다.

검증에서 3 회 재시작 후 리스트 길이와 오브젝트 수가 변하지 않음을 확인했다.

### 렌더 예산

`brush_stamp` 는 60fps 기준 프레임당 약 250 회가 한계다
([knowledge/07 §brush_stamp 타일 렌더러](../../knowledge/07-runtime-quirks.md#brush_stamp-타일-렌더러--매-프레임-252-칸-재그리기도-62fps-스크롤-게임-예산)).
TILE=24 로 화면에 21×12 칸만 그려서 **평지에서 프레임당 45 스탬프**를 쓴다 — 예산의 18%.
지하처럼 밀도가 높은 구간은 ~120 칸이고 실측 61.8fps 다
([타일 크기별 실측표](../../knowledge/07-runtime-quirks.md#brush_stamp-렌더-예산은-방문-칸이-아니라-그린-칸으로-센다--타일-크기를-바꾸면-다시-재야-한다) —
예산은 방문 칸이 아니라 **그린 칸**으로 센다).

### 타일맵 표현

레벨은 문자열 리스트(`lvl`) 12 행이다. 읽기는 `charAt`, 한 칸 쓰기는 `substr`+`combine`
(`replace_string` 은 같은 문자를 모두 바꿔서 못 쓴다). 화면 안 칸만 도는
꼬리재귀 값함수로 스캔한다.

`charAt`/`substr` 은 **범위 밖에서 예외를 던져** 그 스레드만 조용히 죽으므로 좌표→문자
함수(`fnTileAt`)가 중첩 `if_` 로 경계를 먼저 막는다 —
[knowledge/07 §char_at·substring throw](../../knowledge/07-runtime-quirks.md#char_at--substring-은-범위를-벗어나면-throw--문자열-타일맵에-가드-필수).

이 설계 계열(맵=리스트, 충돌=AABB 질의 + 서브스텝 스윕, 액터=고정 길이 병렬 리스트) 전체
해설은 [knowledge/04 §문자열 타일맵 + 서브스텝 스윕](../../knowledge/04-script-and-blocks.md#문자열-타일맵--서브스텝-스윕-충돌--사이드스크롤-플랫포머).

### ⚠️ `_002`(TILE=24) L4 상태 — 재검증 미완

Phase 2-1 에서 타일 배율이 바뀌었으므로 아래 "L4 실패 5 건" 표는 **`_001` 기준 기록**이다.
`_002` 로는 시나리오 [0]~[2] 까지만 돌렸다:

| 시나리오 | `_002` 결과 |
| --- | --- |
| [0] 부팅·HUD | ✅ 통과 (stamps 45, `lvl` 12 행) |
| [1] 이동·관성 | 걷기 이동량 단정 1 건 — 옛 32px 기준(60px)을 `1.6 * TILE` 로 고쳤으나 **재측정 안 함** |
| [2] 가변 점프 | ✅ 통과. 짧게 47px / 길게 112px = **4.7 칸으로 원작 비율 유지** |
| [3] 좌우 벽 충돌 | ❌ 봇이 44 열에서 멈춰 목표(88 열)에 못 감. 뒤따르는 3 건은 벽이 없는 지점에서 판정한 파생 실패 |
| [4]~[15] | 미실행 |

[3] 의 원인은 **가려내지 못했다**. 44 열은 공중 벽돌 줄(행 6)이 있는 곳인데 머리 여유가
39px 로 계산상 막히지 않고, 지형은 스케일 변경 전과 같다(언덕은 여전히 92 열). 게임 결함인지
봇 조작 정밀도인지 판정하려면 Phase 2-3 의 물리 트윈이 필요하다 — 아래 5 건과 같은 계열이고,
그게 트윈을 도입하는 이유다. 봇을 더 튜닝해 통과시키는 건 같은 함정의 반복이다.

### L4 시나리오 16 개

```bash
node games/brick-kingdom/verify.mjs              # 전체 (시나리오마다 새 프로세스)
node games/brick-kingdom/verify.mjs --only 6     # 하나만
```

0. 부팅·타이틀·HUD — TITLE 진입, 생명 3, lvl 356 열, 렌더 예산
1. 좌우 이동 — 걷기/달리기 최고 속도 차이, 스키드 관성, face 전환

3. 좌우 벽 충돌 — 양쪽 벽에서 전진·후진 정지, 접지 유지, 속도 소멸
4. 천장 머리박기 · 보상 블록 1 회성 · **벽돌 조건부 파괴** · 파워업 획득
5. 카메라 — 전진 스크롤, 역스크롤 없음, 월드/카메라 좌표 분리
6. 적 — 위에서 밟기(중복 판정 없음), 셸 정지, 셸 차기, 셸 비행

11. 시간 초과 — `death_cause=4`
12. 반복 재시작 위생 — 리스트 길이·오브젝트 수 불변
13. **셸 연쇄 처치** — 두 마리를 차례로 밟아 셸 2 개를 만들고, 뒤의 셸을 차서

14. 발사체(빔) — 보상 블록에서 빔 획득 → `power=2` → X 발사 → 적 처치
15. 골 도달 — 깃대(350 열) 접촉으로 STAGE_CLEAR, 클리어 연출 후 순환

#### 봇 조작에서 실측으로 확정한 것

검증 코드가 게임을 "조작해서" 확인하려면 실제 사람과 같은 제약을 받는다.
일반화한 지침은 [knowledge/05 §액션 게임을 봇으로 플레이해서 검증](../../knowledge/05-host-editor.md#액션-게임을-봇으로-플레이해서-검증하기)
에 정리했고, 이 게임 고유의 실측만 옮기면:

- **적 활성 범위(±64px)** 때문에 멈춰서 적을 기다릴 수 없다 — 화면 밖 적은
  얼어붙어 있고 카메라가 밀려야 움직인다. 그래서 항상 전진하며 접근한다.
- **밟기 타이밍**: 발동 거리 120~150px + 점프 유지 160ms 에서 3/3 성공.
  45~95px 에서는 적 뒤에 착지하고, 250ms 유지는 적이 밑을 지나가 버린다.
- **셸 차기 방향은 봇이 통제할 수 없다.** 접촉 프레임의 `px < en_x` 로 정해지고,
  밟기 직후 플레이어는 항상 셸의 오른쪽에 있어 차기는 늘 왼쪽으로 간다.
  가속 0.074/frame 으로는 차기 금지 잠금 10 프레임 안에 접촉 폭 26px 을 못 넘는다.
  그래서 연쇄 시나리오는 방향을 바꾸려 하지 않고 **왼쪽에 표적을 만든다**
  (앞의 적을 먼저 셸로 세워 두고 넘어가 뒤의 적을 밟는다).

**검증 원칙**: 모든 시나리오는 `document` 키 이벤트만으로 게임을 조작하고 변수는
읽기 전용으로 관찰한다. 게임 변수를 정답 값으로 강제하지 않는다. 유일한 예외는
`time_left` 인데, 400 초를 실제로 기다릴 수 없어 **남은 시간만** 줄이고 타임아웃
판정(`death_cause`·상태 전이)은 게임이 스스로 하게 둔다.

## 알려진 차이 · 남은 작업

원작(*1985년 그 게임*, 참고 구현 [SuperMarioBros-C](https://github.com/MitchellSternke/SuperMarioBros-C))
대비 재현하지 않았거나 다른 부분을 숨기지 않고 적는다.

### Phase 1 에서 의도적으로 뺀 것

- **파이프 진입 이동** — 파이프는 지형으로만 존재하고, 아래로 들어가는 전환은 Phase 2.
  요구된 L4 항목 중 "파이프 또는 구역 전환"은 Phase 1 에서 **구역 전환**(골 도달 →
  STAGE_CLEAR → 다음 스테이지 순환)으로만 확인했다. 파이프 이동은 Phase 2 에서
  구현하고 같은 시나리오에 추가한다.
- **움직이는 발판 · 무너지는 발판 · 보너스 구역 · 수중 물리** — Phase 2.
- **파이프에서 나오는 적 · 공중 궤도 적(`f`)** — 스프라이트와 로직 슬롯은 있지만
  Phase 1 스테이지에 배치하지 않았다.
- **효과음 · 음악** — 없다. 원작 멜로디·효과음을 복제하지 않는다는 제약에 따라
  자작 효과음을 넣기 전까지는 무음이다.

### 엔진 특성에서 오는 차이

- 원작은 1/256 px/frame 고정소수점이다. 여기서는 실수 px/frame 으로 변환하고
  타일 크기 차이(16 → 24)만큼 1.5 배 했다. 감각은 같지만 값이 비트 단위로 같지는 않다.
  배율은 `physics.mjs` 의 `S` 하나에서 유도한다 — 길이 상수(히트박스·서브스텝·카메라)까지 포함해서.
- 원작의 화면 단위 스크롤 락(구역별 카메라 정지)은 넣지 않았다 — 연속 스크롤이다.
- 적 활성화는 원작의 "화면 진입 시 1 회 활성" 이 아니라 **매 프레임 범위 검사**다.
  결과는 비슷하지만 화면을 되돌아가면 적이 다시 활성화된다.

### 자동 검증으로 확인하지 못한 것

- **골 도달 → 클리어 → 다음 스테이지 순환** — 구현돼 있으나(`goalCheck` → STAGE_CLEAR
  → `dbg_clear`) 봇이 골 앞 계단을 넘지 못해 런타임 확인은 미완이다.
- **빔 발사** — 간헐적으로 통과한다(획득·발사·적 처치를 실제로 관측한 실행이 있다).
- **왼쪽 벽 충돌** — 오른쪽 벽은 확인됐고 좌우 판정은 같은 `fnMoveX` 를 쓴다.

### 다음 작업 (Phase 2 ~ 5)

전체 계획은 [`기획/Phase2-4-계획.md`](기획/Phase2-4-계획.md) 에 있다.

- **2-1 타일 스케일 (완료)** — TILE 32 → 24, 12 행, `S` 1.5. 원작 13 행에 근접한 세로 어휘를
  얻는 게 목적이었다. 실측·결정 근거는 계획 문서 §4.
- 2-2 레벨 데이터를 그리드 → **명령 스트림**으로 (32 스테이지면 문자열 그리드가 ~900KB).
  `levels.mjs` 가 컴파일러가 된다.
- 2-3 **물리 트윈 + 솔버** — 순수 JS 로 물리를 복제해 BFS 로 클리어 가능성·소요 프레임·
  요구 정밀도를 뽑고, L4 는 봇 즉흥 플레이 대신 **트윈이 증명한 경로를 재생**한다.
  아래 "확인하지 못한 것" 의 봇 정밀도 문제가 여기서 정리된다.
- 2-4 ~ 2-6 구역 전환(파이프·보너스), 신규 메커니즘(움직이는·무너지는 발판, 수중), 월드 1 완성.
- Phase 3 ~ 4 월드 2~8. 각 스테이지는 솔버 통과를 커밋 조건으로 삼아 난이도 커브를 정량 관리한다.

## 에셋과 라이선스

**외부 에셋을 쓰지 않았다.** 모든 그래픽은 이 저장소의 코드가 생성한다.

- [`assets/pixel-art.mjs`](assets/pixel-art.mjs) — 문자 격자 → PNG 데이터 URI 변환기
  (`px()` 함수, 팔레트 기반).
- [`assets/sprites.mjs`](assets/sprites.mjs) — 캐릭터·적·아이템·타일 도트 정의.
  타일은 12 도트 × scale 2 = 24px 로 격자와 정확히 맞춘다. 캐릭터·적·아이템도 scale 2.
  정수배가 아닌 확대(16 도트 × 1.5)는 도트를 흐리게 만들어서, TILE 을 24 로 줄일 때
  아트 자체를 12 도트로 다시 그렸다.

주인공 **"코그"** 는 배관공 연상 요소를 피해 설계했다: 청동·황동 색조의 탐험가형
로봇으로, 멜빵바지·모자·콧수염 실루엣을 쓰지 않는다. 적 3 종(롤스톤·코그워커·
스파이크샤드)도 원작 적의 리컬러가 아닌 독자 실루엣이다.

사운드는 아직 없다 — 원작 음원을 복제하지 않으며, 넣을 때는 자작 효과음이나
이용 조건이 명확한 에셋만 쓰고 이 문서에 출처·라이선스·수정 여부를 적는다.
