# 음악 시작을 기준으로 장면과 자막 맞추기

음악 동기화는 **실제로 재생 중인 음원의 위치**에 장면과 자막을 대조한다.
로딩 완료나 시작 버튼을 누른 시각은 음악의 0초와 다를 수 있다.
이 문서는 2026-09-15 로컬 Entry 작품에서 검증한 측정·수정 절차다.
엔진의 초시계 동작은 [07](07-runtime-quirks.md#프로젝트-초시계의-원점과-표시값은-다르다),
소리 필드는 [03](03-objects-and-assets.md#sound)이 정본이다.

## 1. 서로 다른 시간을 따로 기록한다

| 값 | 기준과 용도 |
| --- | --- |
| loadMs | 검사 도구의 로드 함수 소요 시간. 설정된 추가 대기도 포함하므로 음악 오프셋으로 쓰지 않는다 |
| runMs | 시작 버튼 실행 직전부터의 경과 시간. 준비 동작을 포함한다 |
| musicMs | 본 재생 SoundJS 인스턴스의 getPosition(). 음악에 대한 장면·자막 오차 계산에 쓴다 |
| timerMs | 작품 초시계의 마지막 저장값. 블록이 읽는 값과 순간 갱신 지연을 확인한다 |
| freshTimerMs | 실행 중 원점에서 다시 계산한 진단값. 초시계 원점 차이와 표시값 지연을 구분한다 |

로드는 `await Entry.loadProject(project)`로 완료를 기다린다. 임의로 몇 초 더 기다린 뒤
그 시간을 자막 전체에 더하거나 빼는 방식으로 수정하지 않는다. 추가 대기 0과 충분한 대기 조건을
각각 시험하면 로드 준비와 작품 자체의 지연을 구분할 수 있다.

## 2. 작품이 실제로 호출하는 음악을 관찰한다

확인한 `play_bgm` 블록은 기존 BGM을 멈춘 뒤 `Entry.Utils.playBGM(sound.id)`가 반환한
SoundJS 인스턴스를 등록한다. `playSound`만 감시하면 이 경로가 빠질 수 있다.
근거: [block_sound.js](https://github.com/entrylabs/entryjs/blob/53e121523760f15961cd14ab7cb93563a79eaab3/src/playground/blocks/block_sound.js#L843),
[utils.js](https://github.com/entrylabs/entryjs/blob/53e121523760f15961cd14ab7cb93563a79eaab3/src/util/utils.js#L2802).

- 계측 래퍼는 원래 함수에 같은 this·인자를 전달하고 원래 반환값을 돌려준다. 검증 종료 시 복구한다.
- 호출별 음원 id·인스턴스·playState·runMs를 남긴다. 이어지는 정지와 재시작도 추적한다.
- 본 재생의 `playSucceeded`와 계속 증가하는 getPosition()을 확인한다.
  준비 구간은 musicMs를 null로 두어 음원의 0초로 오인하지 않게 한다.
- 소리 등록·디코딩, 사용자 제스처 이후 AudioContext의 running 상태와 비영 출력 파형도 확인한다.
  검사 코드가 직접 다른 소리를 틀어 작품의 기본 블록 실행을 대신하지 않는다.

이 사례에는 준비용 play/stop 20회 뒤 본 재생이 있어 총 21회 호출이 정상이다.
**20회 준비는 엔트리의 필수 절차가 아니라 해당 작품의 구현**이다. 단순히 첫 호출을 기준으로 잡거나
호출이 여러 번이라는 이유만으로 중복 재생 오류라고 판정하지 않는다. 여러 곡을 재생하는 작품은
마지막 호출 하나를 무조건 고르지 말고 큐와 인스턴스의 관계를 명시한다.

## 3. 영상의 실제 프레임 시각을 기준으로 삼는다

0.5초 간격 비교 이미지는 구간을 찾는 데 적합하지만 자막의 최초 등장 시각을 확정하기에는 거칠다.
문구가 바뀌는 근처를 원본 프레임에서 확인하고 프레임 번호 또는 PTS를 보관한다.
고정 24 fps이며 첫 프레임 시각이 0인 자료는 `t = frameIndex / 24`를 쓸 수 있다.
가변 프레임 영상이나 시작 PTS가 다른 자료에는 이 공식을 그대로 적용하지 않는다.

교체 음원과 영상 음성의 시작도 확인한다. 디코딩한 파형의 동일 구간을 비교하면 콘텐츠 오프셋을
검사할 수 있다. 이 사례의 MP3 start_time은 약 25 ms였지만, 디코딩 파형은 영상과 지연 0에서
상관계수 약 0.9990이었다. **컨테이너의 start_time만 보고 자막을 25 ms 이동하지 않았다.**
이 결과는 분석한 구간·파일에 한정되며 두 파일 전체의 길이와 속도가 항상 같다는 보장은 아니다.

## 4. 상대 대기 합과 실제 출력 시각을 구분한다

`wait(2.0)`을 `wait(0.8) + wait(1.2)`로 나누면 숫자 합은 같지만,
새 블록의 재개·반복·조건 평가에 틱이 더 들어갈 수 있다.
따라서 **대기 합 보존은 정적 검사이고 뒤쪽 출력이 안 밀린다는 실행 증거는 아니다.**
세부 비용은 [07의 반복·wait 동작](07-runtime-quirks.md#반복하기-블록--1-프레임반복-60fps-암묵-틱)을 따른다.

음악이 계속 흐르는 작품에는 다음 방법을 검토한다.

1. 본 음악 재생과 같은 초기화 스택에서 초시계 원점을 한 번 맞춘다. 이 사례는 최종 play_bgm 직후
   RESET·START를 실행했고, 실제 음악 위치와 원점 차이를 별도로 검증했다.
2. 장면 전환과 자막에 음악 기준 목표 시각을 둔다. 상대 구간 길이를 계속 더하는 대신
   `남은 대기 = max(0, 목표시각 - 현재 음악 기준 시각)` 또는 목표 시각 도달 조건을 쓴다.
3. 기존 RESET을 바꾸기 전에 **초시계를 읽고 쓰는 모든 스택**을 찾는다. 장면별 0초를 기대하는
   조건은 절대 시각 또는 `현재시각 - 구간시작`으로 함께 바꿔야 한다.
4. 반복 장면은 `scene + visit`으로 구분한다. 장면 길이 합산이나 방문 간격 임계값으로 회차를 추정하지 않는다.
5. 블록 적용 지연을 보정할 때는 근거와 범위를 남긴다. 이 사례의 수십 ms 보정값을 엔진 상수로 재사용하지 않는다.

이 방식은 그림의 이동·모양 애니메이션까지 자동으로 음악에 동기화하지 않는다.
수정한 장면·자막 범위와 유지한 동작을 별도로 검증한다. 재시작·중간 장면 실행·일시 정지·탭 백그라운드에서
음악과 시계를 어떻게 처리할지도 정해야 한다. 이번 실측은 **첫 장면부터 일시 정지 없이 재생**한 범위다.

## 5. 동기화 검증은 장면·자막·시계로 나눈다

requestAnimationFrame에서 보이는 문자열과 장면의 **변경 이벤트**를 기록한다.
장면 이름뿐 아니라 방문 순서, cue id, musicMs, runMs를 함께 남기고 기대 순서·개수·내용도 대조한다.
검사 대상이 61번인데 60번만 관측됐다면 평균 오차가 작아도 실패다.
이는 브라우저에서 관측한 상태 변경 시각이며 실제 디스플레이의 광학적 출력 측정은 아니다.

`오차(ms) = 변경 이벤트의 musicMs - 목표 프레임 시각(ms)`

음수는 빠른 출력, 양수는 늦은 출력이다. 최대 절댓값과 구간별 부호를 함께 보면
고정 오프셋·누적 지연·특정 장면 진입 지연을 구분하기 쉽다.
스크린샷 요청은 한두 프레임 늦게 완료될 수 있으므로 0.5초 간격 캡처로 ms 정확도를 주장하지 않는다.
캡처는 글자 잘림·내용·그림 대응의 육안 검토에도 사용한다.

표시 초시계의 순간 차이만 커졌다면 [07의 원점 진단](07-runtime-quirks.md#프로젝트-초시계의-원점과-표시값은-다르다)으로
분리한다. 표시값만 기록한 옛 자료는 원점 검사 **미측정**으로 남긴다.
검증기의 의미를 고쳤다는 이유로 실제 장면·자막 오차 허용치를 함께 넓히지 않는다.

### 재현 조건과 결과

[최소 실측 근거](evidence/music-sync-20260915.json)는 원본 파일·로그의 SHA-256과 집계값을 담는다.
원본 대본·음원·이미지는 공개하지 않는다. [10의 정적 뮤직비디오 사례](10-music-video-case-study.md)와
다른 파일에서 얻은 실행 기록이며, 10의 검증 상태를 바꾸는 근거가 아니다.

| 조건 | 본 음악 시작 runMs | 장면 24회 최대 오차 | 대상 자막 61회 최대 오차 | 원점 최대 차이 |
| --- | ---: | ---: | ---: | ---: |
| 기본 준비 20회, 전 구간 재생 | 335.4 ms | 18.7 ms | 44.7 ms | 미측정 |
| 준비 100회, 화면 캡처 포함 | 1,601.1 ms | 47.4 ms 미만 | 55.4 ms 미만 | 미측정 |
| 준비 100회, 로드 뒤 추가 대기 0, 원점 계측 | 1,602.0 ms | 29.4 ms 미만 | 36.7 ms 미만 | 7.7 ms 미만 |

준비 100회는 메모리에서만 바꾼 시험 조건이다. 배포 파일과 음원 바이트는 그대로 유지했다.
장면·자막 기준은 80 ms 미만, 원점을 기록한 검사는 40 ms 미만으로 유지했다.
이 합격선과 결과는 해당 로컬 환경의 검사 범위다. 모든 자막 조각, 물리 스피커 지연,
공식 웹 업로드 후 실행, 다른 PC의 성능을 보증하지 않는다.

시계 수정 직전 파일과 비교한 [구조 검사](01-binary-format.md#기존-작품의-일부만-수정하기)에서는
tar 1,831개 중 project.json만 변경됐고, 블록은 2,888개에서 2,914개로 26개 늘었다.
장면 17개·오브젝트 185개·글상자 31개와 음원 바이트는 유지됐다.
정적 구조 보존과 음악 기준 실행 검사는 각각 따로 통과해야 한다.
