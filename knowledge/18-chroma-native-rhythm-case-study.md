# CHROMA 사례 — 기본 블록으로 만드는 리듬게임

2026-09-20 제작·검증한 `CHROMA · PRISM EDITION`의 `.ent` 설계 사례다.
범위는 작품 안의 채보·판정·음악·화면 상태·검증이다. 웹 플레이어 UI와 사이트 배포는 다루지 않는다.
개별 구현과 로컬 관측을 엔트리 모든 버전의 보장으로 일반화하지 않는다.

JSON pointer 단언과 실행 집계를 담았다. 이번 지식 반영에는 게임 원본·에셋·사이트 코드를 포함하지 않는다.
원본을 보유한 환경에서 구조를 다시 검사하는 방법은 [근거 재검사](#7-근거-재검사)에 있다.

## 2. 채보·이동·판정은 같은 시간축을 쓴다

채보는 난이도별 데이터를 하나로 합친 병렬 리스트 `times`, `colors`, `accents`로 저장한다.
`counts = [104, 204, 284, 16]`, `offsets = [0, 104, 308, 592]`로 각 구간을 찾는다.
엔트리 리스트는 1부터 읽으므로 `chartOffset + next`가 실제 인덱스다.
리스트를 읽기 전에 `next ≤ total`을 **바깥 조건문**으로 검사한다.
단락 평가에 기대면 안 되는 이유는 [07 조건 평가](07-runtime-quirks.md#boolean_and_or에-단락-평가short-circuit-없음)에 있다.

아래 식은 설명용이며 실제 작품에는 계산·변수·리스트 블록으로 들어간다.

```text
beatSeconds = 60 / BPM
raw         = base + projectTimerSeconds
time        = raw + inputOffsetMs / 1000
delta       = time - noteTime
noteX       = hitX + (noteTime - time) * travelUnitsPerSecond
```

이 작품은 `hitX = -100`, 이동 속도 180, 첫 노트 시각 4박을 사용한다.
노트마다 `wait`를 누적하거나 매 프레임 고정 거리를 빼지 않고 목표 시각으로 위치를 다시 구한다.
음원 진행·구간 연출·종료는 `raw`, 노트 위치·판정은 입력 보정을 적용한 `time`을 사용한다.
싱크 옵션은 노트와 판정의 관계를 함께 옮기고 음악 재생 위치를 바꾸지 않는다.
음악 시각과 초시계 원점의 구분은 [16 음악 동기화](16-music-synchronization.md)가 정본이다.

입력 처리에서 색 선택을 먼저 갱신하고 다음 노트를 검사한다. 허용 범위 밖의 이른 입력은 색만 바꾼다.
범위 안에서는 올바른 색을 판정하고, 틀린 색은 그 노트를 미스로 소비한다. 판정된 노트는 `next`를
한 번 증가시킨다. 만료 처리도 같은 인덱스를 사용해 한 노트가 타격·미스로 중복 집계되지 않게 한다.

| 판정 | 이 작품의 조건 |
| --- | --- |
| PERFECT | `abs(delta) ≤ 0.055초` |
| GREAT | 그 밖의 `abs(delta) ≤ 0.105초` |
| GOOD | 그 밖의 난이도별 허용 범위 안 |
| 최종 범위 | WARMUP ±220 / STANDARD ±170 / OVERDRIVE ±145 / 연습 ±240 ms |

현재 점수와 최종 점수 모두 **전체 채보 수**를 분모로 사용한다. 실패 시 미처리 노트를 분모에서 빼면
곡 초반에 실패해도 높은 정확도가 나올 수 있다. 최고 기록은 난이도별 실행 중 리스트이며,
연습·자동 연주를 기록 경로에서 제외한다. 정지·새로고침 뒤의 영구 저장으로 설명하지 않는다.

## 3. 일시정지는 저장 시각과 복귀 대기를 분리한다

| 상태 | 값 | 핵심 동작 |
| --- | ---: | --- |
| 메뉴 | 0 | 난이도·모드 선택 |
| 연주 | 1 | `base + 초시계`로 진행 |
| 일시정지 | 2 | 진행·입력 판정·음악 정지 |
| 결과 | 3 | 최종 집계 표시 |
| 안내 | 4 | 조작 안내 |
| 복귀 카운트 | 5 | 저장된 곡 시각을 유지하고 카운트만 진행 |

실제 네이티브 함수의 순서는 다음과 같다. `sound_from_to`는 초 단위의 시작·끝 구간을 받는다.

```text
pause:
  base = raw
  초시계 STOP
  모든 소리 정지
  state = 2

resumeCountdown:
  초시계 START, RESET
  state = 5
  0.5초씩 3카운트 표시

resume:                     // 카운트가 1.5초에 도달한 뒤
  초시계 RESET
  sound_from_to(곡, base, 곡 끝 시각)
  state = 1
```

카운트에 쓴 1.5초를 곡 진행 시간에 더하지 않는 것이 핵심이다. 재개 직전에 초시계를 다시 0으로
맞추고, 저장한 `base`부터 음악과 게임 시간을 함께 이어 간다. START·RESET의 정확한 의미는
[07 초시계](07-runtime-quirks.md#프로젝트-초시계의-원점과-표시값은-다르다)를 따른다.

짧은 상태 갱신 시퀀스는 동기 반환 함수 안에서 처리했다. 반환 함수의 호출·틱 특성은
[07 함수 실행](07-runtime-quirks.md#함수-호출은-반복하기의-60fps-틱을-우회-꼬리-재귀-최적화)을 참조한다.
`fn.value`를 명령문 위치에 직접 넣지 않고 `setVar('sink', call(...))`처럼 값 슬롯에서 호출한다.
반환 함수에 대기·장시간 순회를 추가하는 것은 별도 검토가 필요하다.

## 4. 선명한 자산과 초기 화면도 작품 데이터다

### 래스터 해상도와 무대 배율

타이포·도형은 논리 좌표를 유지한 SVG로 작성하되 물리 크기를 3배로 내보냈다.
논리 480×270 배경은 1440×810 PNG로 번들하고 엔티티 배율은 `1/3`으로 둔다.
노트는 96×96 PNG에 같은 배율을 적용해 무대에서 32×32가 된다.
원본 해상도·`dimension`·배율을 함께 맞춰야 확대 표시에서 그림만 커지거나 흐려지는 문제를 피할 수 있다.
3배는 이 작품의 선택이며 모든 이미지에 필요한 엔진 상수가 아니다.

**이미지 픽셀 수와 실제 무대 크기는 별개다.** 1254×1254 프리즘 PNG는
`207 / 1254` 배율을 적용해 무대에서 약 207×207로 표시한다.
SVG→PNG 번들 규칙과 투명 이미지 검사는 [03 자산](03-objects-and-assets.md)이 정본이다.
최종 `.ent`의 PNG 치수와 배율도 근거 단언에 넣었다.

### 크기 블록으로 막대 높이만 바꾸지 않는다

`setSize`는 [폭·높이 평균을 맞추는 블록](07-runtime-quirks.md#크기-정하기는-퍼센트가-아니다)이라
가로 폭도 함께 변한다. 결과 그래프는 폭 8·높이 20의 동일 캔버스 안에서
채운 높이만 다른 20개 모양을 만들고 `ceil(binCount / maxCount * 20)`으로 선택한다.
빈 bin은 숨긴다. 막대 폭·바닥 기준선을 유지하면서 높이를 바꿀 수 있다.
실제 렌더에서 제목과 최댓값 막대가 겹친 문제도 수정했다. 개수 검사와 화면 검수는 별개다.

### 시작 버튼을 누르기 전부터 타이틀이 보여야 한다

`when.run`의 `hide`만으로는 정지 상태 화면을 정의할 수 없다. 처음부터 타이틀 구성 오브젝트
9개만 `entity.visible: true`, 나머지는 `false`로 직렬화했다. 채보와 내부 값도 **변수·리스트
82개 모두** `visible: false`로 저장한다. 시작 전·시작 후·저장 후 재불러오기 상태를 따로 확인했다.
그래픽 버튼의 문구와 실제 키·클릭 동작도 같은 상태표로 대조한다.

## 5. 연출과 통계는 판정 결과에서 파생한다

FLOW는 성공 판정 때 충전하고 미스 때 초기화한다. 발동 시 `flowUntil = raw + 8 * beatSeconds`로
끝 시각을 정하고, `raw < flowUntil`인 동안 활성화한다. 프레임 수로 8박을 세지 않으므로
정지 상태에서 효과의 남은 곡 시간이 줄어들지 않는다. 점수 배율은 바꾸지 않고
정타의 신호 회복량과 연출만 바꾼다.

타격 이펙트는 `raw - hitAt`, 구간 타이포는 `raw - sectionStart`로 위치·투명도를 계산한다.
곡 시간과 무관한 타이틀 부유·결과 점수 카운트에는 프레임 기반 연출을 썼다.
이 둘을 구분하면 장식 애니메이션의 속도가 판정 시간에 영향을 주지 않는다.

성공한 입력의 부호 있는 오차를 ms로 반올림해 평균과 14개 bin에 누적한다.
평균이 음수면 이른 입력, 양수면 늦은 입력이다. 미스는 성공 오차 분포에 넣지 않는다.
결과에는 분포뿐 아니라 PERFECT/GREAT/GOOD/MISS와 전체 채보 기준 정확도를 함께 표시한다.
평균 한 개가 많은 미스를 가리거나 반대 방향의 오차를 상쇄할 수 있기 때문이다.
재도전은 점수뿐 아니라 분포·최댓값·평균·FLOW 횟수·표시 애니메이션 상태도 초기화한다.

## 6. 자동 연주 성공과 키 입력 완주는 다른 증거다

| 검사 | 조작 방식 | 이 사례의 확인 범위 |
| --- | --- | --- |
| 판정 경계 fixture | `next`·`base`를 배치한 뒤 실제 키 이벤트 | PERFECT/GREAT/GOOD, 틀린 색, 이른 전환, 만료 |
| 내장 자동 연주 | 게임의 자동 판정 경로 | 고밀도 284노트, 6구간, 종료 집계 |
| 키 입력 전곡 | 상태 읽기 + keydown/keyup만 사용, 게임 상태 쓰기 없음 | STANDARD 204노트, 색 전환·edge 감지·최고 기록 |
| 실제 클릭 | 캔버스 좌표로 마우스 클릭 | 시작·안내·연습·복귀·재도전 |
| 편집기 왕복 | 원본 편집기에서 열기·실행·저장·다시 열기 | 모양·소리 참조, 블록, 정지 화면, 연습 재실행 |

`isPressed`를 프레임마다 검사하는 입력은 down/up을 같은 순간에 보내면 관측하지 못할 수 있다.
검증은 일반 tap에서 40ms 누름·45ms 해제 대기, 전곡 입력에서 약 35ms 누름을 사용했다.
이 숫자는 검사 조건이며 키 입력 지연이나 모든 실행 환경의 최소값이 아니다.
키 **해제 상태도 게임이 관측하도록** 하고 점수·콤보·노트 소비로 입력 도달을 확인한다.
이벤트 전달 경로는 [07 키 이벤트](07-runtime-quirks.md#키-이벤트는-document--eventcode-로-dispatch)가 정본이다.

로컬 실행 기록은 게임 검사 65개와 편집기·패키지 검사 9개를 통과했다. 자동 연주는
284콤보, 키 입력 전곡은 204콤보이며 각각 1,000,000점·100%였다. 음원 8개 모두 등록·디코딩됐고
네이티브 음악 블록 출력과 음소거도 확인했다. 소리 검증 절차는 [15](15-audio-verification.md)를 따른다.

동기화는 구간 6곳과 재개 뒤 1곳에서 `구간 시작 오프셋 + SoundJS 위치`와
`base + 원점으로 새로 계산한 초시계`를 비교했다. **이 7개 관측의 최대 절댓값은 약 9ms**,
검사 허용치는 80ms였다. 전체 시간의 연속 상한, 물리 스피커 지연, 다른 PC의 성능을 뜻하지 않는다.
공식 웹 게시·별도 공식 오프라인 앱·사람의 청취·탭 백그라운드 동작은 이 파일에서 검증하지 않았다.

## 7. 근거 재검사

원본 보유자가 프로젝트 루트에서 실행한다. 경로는 자신의 파일 위치로 바꾼다.

```powershell
node tools/verify-case-study-evidence.mjs --source "C:/작품/chroma_009.ent" --evidence knowledge/evidence/chroma-prism-20260920.json
```

검증기는 원본 해시와 `assertions`의 구조를 대조한다. 게임을 실행하거나 `localRuntime`의
역사 집계를 다시 측정하지 않는다. 원본과 전체 실행 로그가 없는 공개 사본에서는 실행 결과를
재현했다고 주장하지 않는다. 근거 공개 범위와 정적 검증 방식은 [evidence 안내](evidence/README.md)를 따른다.
