## 1. 도로 모델 — 500단위 구간과 미리 곱한 리스트

한 리스트 항목이 도로 한 구간(500 world units)이다. `길 굽기`(곡률), `길 높이`(구간 앞 경계의 높이),
`길 색 번호`(테마×2 + 짝홀), 길가 물체 2칸(`sp1/sx1`, `sp2/sx2`)을 둔다. 곡률·높이는 **초점거리 K=200을
미리 곱해 저장**해서 투영식의 곱셈을 한 번 줄였다. 리스트 뒤에 처음 52구간을 한 번 더 붙여 두면
한 프레임 안의 구간 번호가 코스 끝을 넘어도 나머지 연산 없이 그대로 읽힌다.

엔트리 좌표(가운데 원점, y 위쪽)에서 경계 n의 투영은 다음과 같다. `z`는 카메라 깊이, `X`는 누적
곡률로 생긴 가로 어긋남(×K), `camX = K·RW·px`, `camY = K·(CH + 차 아래 도로 높이)`.

```
iz = 1 / z
sw = K·RW · iz                 // 화면상 도로 반폭
sx = (X − camX) · iz           // 도로 중심
sy = HOR + (Y[i] − camY) · iz  // 화면 높이 (HOR = 25, 지평선)
X_{n+1} = X_n + dX_n,  dX_{n+1} = dX_n + 곡률[i]   // 곡률은 가로 가속도
```

첫 경계는 카메라 뒤·바로 앞이라 `z`가 0에 가깝다. 경계 1은 `z ≥ 300`으로 잘라 투영하고 재귀는
경계 2부터 시작한다. 경계 1~2 사이 사다리꼴은 화면 아래 밖이라 잘린 값이 보이지 않는다.

## 2. 재귀 한 번에 가까운 곳부터 그리고, 돌아오며 먼 곳부터 찍는다

`band(n, i, z, X, dX, M, 이전 경계 x·폭·y)`는 **보통 함수(문장 블록)**다. 값 함수와 마찬가지로
동기 실행되며([07 함수 호출](07-runtime-quirks.md#함수-호출은-반복하기의-60fps-틱을-우회-꼬리-재귀-최적화)),
재귀 호출 뒤에도 블록을 더 둘 수 있다.

1. **내려가며(가까운 → 먼)**: 경계 n을 투영하고, `sy`가 지금까지 그린 가장 높은 선 `M`보다 높을 때만
   이전 경계와의 사이를 채운다(땅 전폭 → 연석 1.16배 → 아스팔트 → 짝수 구간이면 차선). 낮으면 언덕 너머라
   그리지 않고 `M`을 유지한다. 이것이 언덕 가림이다.
2. **재귀 호출**로 다음 경계로 간다.
3. **돌아오며(먼 → 가까운)**: 이 구간에 들어 있는 라이벌 차(`car`)와 경계 n의 길가 물체를 도장으로 찍는다.

도장은 찍은 순서대로 위에 쌓이므로([§레이어 순서](#3-한-오브젝트-안의-레이어-순서는-만든-순서다))
재귀가 돌아오는 순서가 곧 **화가 알고리즘 순서**다. 정렬도, 그릴 목록 리스트도 필요 없다.
언덕 너머 구간의 차는 자신의 투영 높이가 `M`보다 높을 때만 찍는다. 길가 물체는 기준점이 가려진
구간이면 통째로 생략한다(나타날 때 튀어나오는 근사, 픽셀 단위 잘라내기는 없음).

- **이음새**: 인접 사다리꼴 사이로 배경이 새는 가는 줄이 보였다. 각 구간의 먼 쪽 가장자리를 0.8px
  올려 다음 구간 밑으로 겹치게 해서 없앴다. 다음 구간이 나중에 그려져 겹친 부분을 덮는다.
- **거리 안개**: 먼 구간일수록 노을색으로 섞은 팔레트(4단계)를 `안개 단계` 리스트로 고른다.
  색 번호에 오프셋만 더하므로 투명 레이어 없이 공짜로 흐려진다.
- **차선**: 채우기 사각형 대신 **붓 선**(굵기 = 반폭×0.055, 둥근 끝)으로 그려 블록 수를 절반으로 줄였다.

## 3. 한 오브젝트 안의 레이어 순서는 만든 순서다

붓 선 레이어와 채우기 레이어는 **처음 쓰일 때** 스프라이트 바로 아래에 끼워진다
([utils.js `setBasicBrush`·`setBasicPaint`](https://github.com/entrylabs/entryjs/blob/53e121523760f15961cd14ab7cb93563a79eaab3/src/util/utils.js#L1627)).
도장은 찍을 때마다 스프라이트 바로 아래에 끼워진다
([entity.js `addStamp`](https://github.com/entrylabs/entryjs/blob/53e121523760f15961cd14ab7cb93563a79eaab3/src/class/entity.js#L1630)).
그래서 한 오브젝트 안에서는 **먼저 만든 레이어 < 나중에 만든 레이어 < 모든 도장** 순서가 고정된다.
이 게임은 시작할 때 `채우기 색 정하기`를 `붓 색 정하기`보다 먼저 실행해 차선(붓)이 아스팔트(채우기) 위에,
차와 나무(도장)가 그 위에 오게 했다. 엔진 규칙은 [07](07-runtime-quirks.md#붓-선과-채우기-레이어는-처음-만든-순서대로-쌓이고-도장은-항상-그-위다)에 두었다.

## 4. 도장 스프라이트는 정사각 캔버스 + 크기(px) 계산

길가 물체와 차 그림은 모두 **정사각 캔버스에 바닥 가운데 정렬**로 그렸다(나무 512², 차 256²).
`크기 정하기`는 폭·높이 평균을 px로 맞추는 블록이라([07 크기](07-runtime-quirks.md#크기-정하기는-퍼센트가-아니다))
정사각이면 크기 = 화면 높이가 된다. 물체마다 "캔버스가 세계에서 차지하는 폭×K"를 `물체 크기` 리스트에 두고
`크기 = 물체크기 × iz`, `y = 도로 y + 크기/2`로 찍는다. 모양을 먼저 바꾸고 크기를 정해야 한다
([07 모양 뒤 크기](07-runtime-quirks.md#크기-정하기는-현재-모양의-치수로-계산된다--모양을-바꾼-뒤-다시-정한다)).

라이벌은 `slots`가 매 프레임 "화면 구간 n → 차 번호" 연결 리스트(`구간별 차`, `같은 구간 다음 차`)를 만든다.
차는 구간 안의 비율 f로 경계 n과 n+1 사이를 보간해 매끄럽게 움직이고, 화면 x가 ±30을 넘으면 옆면이 보이는
모양(3방향)으로 바꾼다. 이전 프레임에 쓴 칸만 지우므로 지우기 비용이 차 수(7)에 비례한다.

## 5. 블록 비용을 재고 설계했다

`spike/micro.mjs`로 반복 1회에 같은 블록 10개를 넣은 꼬리 재귀를 돌리고, `Entry.container.mapObjectOnScene`
한 틱의 실행 시간을 쟀다(`spike/micro-run.mjs`). 아래는 **블록 1개당 틱 시간**이며 재귀 자체의 몫
(반복당 전역 쓰기 1 + 함수 호출 1 ≈ 1.25µs/블록)이 포함돼 있다. 같은 PC·같은 엔진에서만 비교한다.

| 블록 (값은 전역 변수 a·b에서 읽음) | µs/블록 | 해석 |
| --- | ---: | --- |
| 전역 `변수 정하기` (상수) | 5.7 | **가장 비싸다** — 숨긴 변수도 매번 모니터 배치 계산 |
| 〃 + 전역 변수 읽기 | 6.2 | 읽기 ≈ 0.5 |
| `+` / `×` (calc_basic) | 7.1 / 7.2 | BigNumber, 연산 ≈ 0.5 |
| `÷` | 8.6 | BigNumber 나눗셈 ≈ 2 |
| `몫·나머지`, `절댓값` | 6.6 / 6.2 | 일반 JS 수학, ≈ 0 |
| 리스트 항목 읽기 | 6.1 | ≈ 0.4 |
| 함수 매개변수 읽기 | 5.5 | ≈ 0 |
| 함수 지역 변수 쓰기+읽기 | 2.1 | 전역 쓰기의 약 1/3 |
| 리스트 항목 바꾸기 | 2.4 | 전역 쓰기보다 싸다 |
| `x: y: 위치로 이동` | 2.8 | |
| 채우기 사각형 1개 (이동 4 + 시작·멈춤) | 11.9 | |
| `채우기 색 정하기` | 2.3 | |
| 모양 바꾸기 / 크기 정하기 / 도장 1세트 | 3.2 / 4.6 / 13.8 | |
| 함수 호출(매개변수 6, 지역 변수 4) + 전역 쓰기 | 12.5 | 호출 ≈ 7 (지역 변수는 호출마다 깊은 복사) |

여기서 나온 설계 규칙:

- **반복 안에서는 전역 변수에 쓰지 않는다.** 구간마다 바뀌는 값은 재귀 **매개변수**로 넘기고,
  한 구간 안의 중간값은 **함수 지역 변수**에 둔다. 전역 쓰기는 프레임당 몇십 번으로 제한한다
  ([07 전역 쓰기 비용](07-runtime-quirks.md#전역-변수-정하기는-숨긴-변수여도-약-5µs--모니터-배치-계산이-매번-돈다)).
- 재귀 **문장** 호출을 쓴다. 값 함수 재귀(`setVar('sink', call(…))`)는 매 단계 전역 쓰기 5µs를 더 낸다.
- 나눗셈(2µs)은 `iz = 1/z` 한 번으로 줄이고 곱셈으로 바꾼다.
- 반대로 "지역 변수 읽기는 비싸니 전부 매개변수로 넘기자"는 가설은 틀렸다. 다음 경계 투영을 호출 인자로
  계산하도록 바꾸자 나눗셈이 늘어 렌더 시간이 6.4 → 6.9ms로 오히려 늘었다(지역 변수 읽기 ≈ 0.4µs).
  측정 없이 최적화하지 않는다.

측정한 프레임 예산(레이스 중, ms/프레임): `render` 6.4, `ai` 0.8, `slots` 0.3, `physics` 0.15, 계기판 0.6
(숫자를 2프레임에 한 번 다시 찍음), 나머지 오브젝트 합 0.2. 구간당 블록 평가가 약 220개라
46구간이면 렌더가 대부분을 차지한다.

## 6. 게임 규칙에서 지킨 조건

- **시간**: 프로젝트 초시계는 별도 60Hz 타이머로 갱신돼 차분이 들쭉날쭉하다
  ([07 초시계](07-runtime-quirks.md#프로젝트-초시계의-원점과-표시값은-다르다)). Δt를 0~0.066초로 자르고
  지수 평활(0.85)해서 모든 이동·랩 시간에 쓴다. 느린 기기에서도 실시간에 가깝게 진행한다.
- **원심력**: `px -= Δt·0.185·속도비²·곡률`, 조향은 `±Δt·2.3·속도비`. 보통 커브(곡률 11)는 최고 속도로
  버틸 수 있고, 급커브(17)는 약 73%까지 줄여야 한다. 이 비율이 "급커브 앞에서만 브레이크"라는 플레이를 만든다.
- **라이벌 차선은 세 차선(−0.62, 0, 0.62)에만 선다.** 출발 그리드(±0.45)를 그대로 차선으로 쓰자 가운데 차선
  차와 접촉 폭(0.52) 안에 겹쳐 추돌이 끝없이 났다. 계산한 목표 차선은 항상 가장 가까운 차선으로 붙인다.
- **추돌은 앞차에만**: 내 차가 뒤에서 들이받은 경우(`0 < 간격 < 430`)만 내 속도를 줄인다. 처음에 간격
  −200~430으로 대칭 판정하자 뒤에서 따라붙은 라이벌이 옆에 겹칠 때마다 내 차가 감속됐다.
- **러버밴딩**: 3,000 이상 앞선 라이벌은 목표 속도 ×0.88, 5,000 이상 뒤처지면 ×1.07. 깨끗한 랩(약 36초)이면
  선두(약 40초)를 이기고, 실수가 쌓이면 추격당한다.
- **자동 주행**은 타이틀(0)과 결승 후(3)에서만 조향한다. 카운트다운(1)까지 조향하자 출발 전 차가 옆 차선으로 흘렀다.

## 7. 소리 — 음악은 BGM 채널, 엔진은 재생 속도

`소리 재생 속도 정하기`는 **재생 중인 모든 효과음**의 속도를 바꾼다. 그런데 `배경음악 재생하기`는
별도 목록(`bgmInstances`)에 들어가고 재생 속도도 적용받지 않는다
([07 BGM과 재생 속도](07-runtime-quirks.md#배경음악-재생하기는-소리-재생-속도의-영향을-받지-않는다)).
그래서 음악은 BGM으로, 엔진음은 일반 소리로 재생해 **음악은 원래 음높이, 엔진은 속도에 따라 0.55~1.9배**로
올렸다(2단 기어 곡선, 가속을 떼면 −0.06). 엔진 샘플은 1초이고 양 끝 60ms 페이드를 넣었다. 현재 재생 속도
기준 0.9초마다 새로 재생해 두 인스턴스가 겹치며 교차 페이드된다. 효과음(충돌·랩·타이어)은 엔진 속도를 따라
음높이가 함께 변하는데 이것은 허용했다. 카운트다운 신호음은 BGM 채널로 보내 음높이를 지켰다.

검증은 [15 소리 검증](15-audio-verification.md) 방식대로 `playSound`·`playBGM` 호출과 최종 출력 파형을
기록했다. 엔진 재생 속도 0.55 → 1.9 상승과 BGM 인스턴스의 재생 속도 1 유지를 함께 단언한다.

## 느린 기기: 적응형 그리기 거리

60프레임마다 평활 Δt를 보고 20.5ms를 넘으면 그리는 구간을 4씩(최소 26), 17.5ms보다 빠르면 2씩(최대 46)
조정한다. 안개 단계 인덱스를 `n + (46 − 구간 수)`로 밀어 짧아진 도로도 끝이 흐려진다.
CDP `Emulation.setCPUThrottlingRate`로 모의한 결과는 2배 제한 40~45 fps(26구간), 4배 제한 13~14 fps다.
4배에서는 프레임 약 75ms 중 블록 실행 몫이 1배 측정값(약 7ms)의 4배를 크게 넘지 않을 것으로 보여, CreateJS 그리기·도장 생성 비용이 큰 것으로 추정한다(분리 측정은 하지 않음). 거리 축소만으로는 부족했고 이 한계는 남아 있다.

## 8. 검증 설계

[verify.mjs](../games/sunset-drive/verify.mjs)는 시나리오마다 새 브라우저 프로세스를 띄운다
([07 재부팅 누적](07-runtime-quirks.md#헤드리스-검증에서-브라우저를-10-회-재부팅하면-키-이벤트가-게임에-도달하지-않는다)).
게임 변수는 읽기만 하고 입력은 `document` 키 이벤트만 보낸다.

- **완주 봇이 게임 버그를 찾았다.** 처음 봇은 2~4위였다. 봇에 "충돌 순간의 가장 가까운 차·가로 간격" 기록을
  넣자 매번 같은 차와 가로 0.45 간격으로 추돌하는 패턴이 드러났고, 원인은 봇이 아니라 위 6절의 **차선 불일치와
  대칭 추돌 판정**이었다. 결과(순위)만 보지 말고 실패 원인을 기록하는 검증이 필요하다.
- **왕복**: 편집기 `exportProject` → `/api/export`로 저장한 파일을 다시 불러와 그림·소리·블록·리스트 개수가
  같고 게임이 다시 도는지 확인한다(사용자가 편집기에서 저장하는 경로).
- **실서비스 엔진 대조**: 전체 파일을 공식 사이트에 올리지 않고, 만들기 화면에서 이 게임이 쓰는 블록 49종과
  실행기·Scope·도장·크기·모양·붓·소리·변수 내부 함수 39개의 소스 해시를 로컬 엔진과 비교했다
  (공백·번들러 이름 정규화). 모두 같았고 차이는 EaselJS `Graphics.clear()`가 `_oldStrokeStyle`을 초기화하지
  않는 것 하나였다. 엔트리의 붓 지우기는 곧바로 새 선 스타일 객체를 만들므로 이 게임에는 영향이 없다.
  두 곳 모두 WebGL이 있어도 붓·채우기를 CreateJS(Canvas 2D)로 그렸다
  ([05 엔진 사본](05-host-editor.md#엔진-사본의-버전-기준-npm-핀과-실서비스의-격차)).
  이것은 **코드 경로의 동일성** 근거이며 공식 사이트에서 실제로 플레이한 증거가 아니다.

## 9. 홍보용 움직이는 썸네일(APNG)

작품 목록에 쓰는 움직이는 썸네일은 실제 실행 화면을 캡처해 만들었다. 파일과 스크립트는 로컬 전용
`games/sunset-drive/thumbnail/`에 두고 공개 저장소에서 제외했다. 썸네일을 적용하는 도구인 Entry Debugger
실험실의 "작품 썸네일 변경"(워크스페이스 `extensions/Entry Debugger/지식/thumbnail-experiment.md`)의 변환 규칙이
설계 조건이었다.

- **변환 예산.** 이 도구는 모든 프레임을 480×270 RGBA 전체 프레임(PNG Sub 필터 + deflate)으로 다시 압축하고,
  합계가 900,000바이트를 넘으면 해상도와 프레임 수를 줄인다. 1/12초보다 짧은 프레임은 앞 프레임에 합친다.
  Chrome이 지연을 정수 ms로 반올림하므로 정확히 1/12초로 만들면 한 장 걸러 사라진다.
  같은 방식으로 인코딩하면 파일 크기가 곧 변환 결과 크기다. 이 게임 화면은 원래 색이면 프레임당 약 96KB라
  9장밖에 들어가지 않았고, 21장이 함께 쓰는 64색 팔레트로 줄이자 약 38KB(21장, 806,799바이트)가 됐다.
- **줄무늬가 멈추거나 거꾸로 간다.** 노면 색은 구간마다 번갈아 1,000단위 주기로 반복된다. 초당 12장 이하로
  시간 간격에 맞춰 찍으면 시속 290km(초당 12,000단위)에서는 한 장마다 정확히 한 주기를 가서 줄무늬가 멈춰 보이고,
  그보다 느리면 뒤로 간다. **달린 거리 1,350단위마다 한 장**을 찍어 줄무늬가 매 프레임 0.2~0.48주기씩 앞으로
  가게 했고, 프레임 지연에는 실제 게임 시간(116~150ms)을 넣었다.
- **그려지지 않는 틱.** 무대 그리기는 실행 틱과 다른 타이머로 돈다. 캡처 부하가 있는 헤드리스에서는 틱의
  약 4분의 1이 화면에 그려지지 않았다. 캡처할 틱에서는 `mapObjectOnScene(computeFunction)`이 끝난 직후
  `Entry.stage.update()`로 그리고 `createImageBitmap`으로 복사했다. PNG 인코딩은 캡처가 끝난 뒤에 한다.
- **팔레트.** ffmpeg `palettegen`은 픽셀 수에 비례해 색을 나눠 작은 라이벌 차의 채도가 빠졌고, sharp는
  `colours`를 256보다 작게 주면 실제로는 16색을 만들었다. OKLab 색 공간의 k-means에 픽셀 수의 제곱근을
  가중치로 쓰고, 넓은 단색 면은 가장 많이 쓰인 원래 색을 그대로 쓰게 했다.
- **검증 범위.** Chrome `ImageDecoder`로 프레임 수·지연·픽셀을, Entry Debugger의 변환 코드로 480×270·21프레임이
  그대로 남는지(`reduced: false`, 픽셀 차이 0)를 확인했다. 엔트리 서버에 저장하지는 않았다.

## 재사용할 때 확인할 점

- 구간 길이·그리는 거리·K·HOR를 바꾸면 경계 1의 `z ≥ 300` 자르기와 안개 단계 표, 차 배치의 가시 범위를 함께 바꾼다.
- 길가 물체를 3개 이상 두려면 `sp3/sx3`와 `band`의 도장 블록, `physics`의 충돌 검사를 같이 늘린다.
- 두 번째 충돌 검사(`점 n+1`만 확인)는 프레임당 이동 거리가 구간 길이보다 짧다는 가정이다(Δt 상한 0.066초에서
  최고 속도 792단위 < 2구간). Δt 상한이나 최고 속도를 올리면 앞 두 점을 검사한다.
- 오브젝트 목록 순서가 표시 순서다. 프로파일에서 한 틱의 실행도 같은 순서(계기판 → … → 월드 → 배경 → 소리)로 관측됐으므로 계기판은 한 프레임 전 값을 그린다.
